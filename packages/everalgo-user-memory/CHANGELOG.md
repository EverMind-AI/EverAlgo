## [Unreleased]

## [0.9.0rc3] - 2026-10-13

### Changed

- The episode, episode-summary, atomic-fact-from-text and reflect system messages close their `<custom_instructions>` block with core's `everalgo.utils.append_custom_instructions`; the private `_render.nonblank` and the callers' guard around it are removed, since the helper skips a blank string itself. Through `EpisodeExtractor`, `EpisodeSummarizer`, `AtomicFactExtractor.aextract_from_text` and `EpisodeReflector` the rendered system message is byte-for-byte unchanged. Only a direct call of a prompt module's `assemble_system_prompt` with an empty or blank `custom_instructions` now leaves the block out (it used to emit an empty block), the same as `None`.
- Requires `everalgo-core>=0.6.0rc3` (the floor was `0.6.0rc2`): the package imports `everalgo.utils.append_custom_instructions`, which `0.6.0rc2` does not define.

## [0.9.0rc2] - 2026-10-13

### Added

- `EpisodeSummarizer.asummarize(episode_text, *, output_language=None, custom_instructions=None) -> str` (sync bridge `summarize`), exported from `everalgo.user_memory` and `everalgo.user_memory.episode`: one LLM call that writes the display preview of an episode text already stored — a body a user edited, or a record from before the extractor produced summaries. The summary is described in one place, `prompts.en.episode.EPISODE_SUMMARY_FIELD_RULE`, which both `EPISODE_SYSTEM_PROMPT` (rendered byte-for-byte as before) and the new `EPISODE_SUMMARY_SYSTEM_PROMPT` are built from, and the result goes through the extraction path's 400-unit sentence-boundary guard, so the two paths store interchangeable previews. A host that keeps its own copy of the summary prompt for these paths, such as the cloud engine's episode-summary service, can call this instead and drop the copy. The reply is held to `{"summary"}`; an invalid or blank one raises `LLMOutputError`, and a blank `episode_text` raises `InvalidInputError` before any call.

### Changed

- Invalid caller input now raises `everalgo.utils.InvalidInputError` (a `ValueError` subclass, so existing handlers keep working) instead of a bare `ValueError`, so a host can treat it as terminal by type: an unknown `output_language`, a message with no timestamp, unsorted or too few episodes for reflection, empty `memcells`, a `sender_id` that is not a user speaker, an `old_profile` of another owner, a blank `owner_id`, an empty or blank-narrative `episodes`, or no episode naming the owner. Each message names the offender (an index, a `sender_id`, an owner id) and what to do about it.
- Requires `everalgo-core>=0.6.0rc2` (the floor was `0.6.0rc1`): the package imports `everalgo.utils.InvalidInputError`, which `0.6.0rc1` does not define.

## [0.9.0rc1] - 2026-10-13

The first release candidate of 0.9.0, and the first release since the 0.8.0 release candidates below (`rc1`-`rc9`); it carries that line onto the new LLM contract of `everalgo-core` 0.6.0rc1. Being a pre-release, it installs only with `--pre` or an explicit `==0.9.0rc1` pin. Every operator now requests its reply as a strict pydantic model, sends a static system message of rules and a user message holding only the data, and renders every time the same way. A host upgrading from `0.8.0rc9` will typically need to implement `LLMClient.achat`, replace `prompt=` with `custom_instructions=` (or nothing), catch `everalgo.llm.LLMOutputError` where it caught `ValueError` or `json.JSONDecodeError` from a reply, and stop reading `Episode.user_language`.

### Added

- `ProfileExtractor` logs what each UPDATE pass did, as `key=value` pairs documented in the `everalgo.user_memory.profile` module docstring and carrying no prompt, model output or item content. The INFO line `profile update applied:` now reports, once per pass, which pass it was (`historical` or `current` on the Episode path, `single` on the MemCell path), the date the pass was judged against, the reply's ops by action, how many were rejected, how many landed updates rewrote a description, only added grounding or appended history, how many add labels were respelled to one on file, the profile's timestamp before and after, and the merged bucket sizes; it replaces the line's former `N ops -> explicit= implicit=` text. A stale-evidence rejection appends the two dates that decided it, `item_observed_at_ms` and `batch_observed_at_ms`. A DEBUG line `profile add label canonicalised:` reports each respelled label by bucket and lengths, never its text. The Episode-path entry line carries `categories=N`, the size of the normalised category snapshot.
- An UPDATE from Episodes older than a stored item may add earlier history to that item's description: an update whose description is the stored one followed by a parenthesis (case- and whitespace-folded, the stored description's closing `.` `!` `?` `。` `！` `？` set aside), such as `Lives in Chengdu (earlier in Chongqing).` over `Lives in Chengdu.`, lands with its evidence, and the item keeps its `observed_at`. It used to be dropped as `reason=stale evidence`, losing the earlier value the model had put into evidence along with it. Any other description change from an older batch (a negation put before the stored words or a contradiction around them included) and any delete is still refused.

### Changed

- **BREAKING:** every operator follows the new `LLMClient` contract (see `everalgo-core`): it passes a strict pydantic model as `response_format`, reads the reply as `str`, validates it with `everalgo.llm.parse_reply`, and calls `achat`, the new name of the protocol method, so a custom client passed as `llm` must implement `achat(messages, *, response_format, ...) -> str` instead of `chat`. A reply that is not exactly that object (prose or a ```` ```json ```` fence around it, a missing or extra key, a mistyped value, a blank required field) raises `everalgo.llm.LLMOutputError` instead of `ValueError`, `json.JSONDecodeError` or a pydantic `ValidationError`; its message names each failing location and never quotes the reply. There is no retry, and whatever the client raises propagates unchanged. Replies that used to be repaired are now rejected, as each operator's entry below spells out.
- **BREAKING:** `ProfileExtractor` requests each stage's reply as its own model (INIT, UPDATE, COMPACT and REGROUP), and a reply that puts an item in a bucket it is not shaped for (an UPDATE `add` or `update` whose `data` does not match its `type`, a REGROUP item not shaped for its group's bucket) or carries an `observed_at` the model wrote into an operation (previously discarded) is rejected rather than repaired. On the Episode path the replies no longer carry `update_note`, `compact_note` or `regroup_note`, which the code never read, so a reply that still writes one fails as an extra key; the MemCell path's prompts still ask for a note and its replies are validated against models of their own that require it. Both paths' item models declare their fields grounding first (`evidence`, `description`, `category`; `basis`, `description`, `trait`), which is the property order of the strict schema each stage requests.
- **BREAKING:** `EpisodeExtractor` requests a strict reply of three fields, in this order: `content`, `summary`, `title`; a blank `title` used to pass and is now rejected. The model no longer declares a language: `user_language` is gone from the reply, the prompt and its language rule, so a reply that still writes `language` or `user_language` fails as an extra key, and the `Episode` carries no `user_language` extra field, whether or not `output_language` is named (a host that needs the episode's language judges it from the text). The `episode language declaration rejected` WARNING is gone and the `episode extracted` INFO line drops `language=`.
- **BREAKING:** `AtomicFactExtractor` requests `{"atomic_facts": {"atomic_fact": list[str]}}`: a non-string fact (previously dropped) or a missing `atomic_fact` (previously an empty list) raises `LLMOutputError`, blank fact sentences are still dropped, and the `event_log` top-level key is no longer accepted, so `EVENT_LOG_PROMPT`, the one prompt that asked for it, is removed. The reply no longer echoes the time: a reply that still writes `time` fails (`atomic_facts.time: Extra inputs are not permitted`); nothing read the echo.
- **BREAKING:** `ForesightExtractor` requests `{"foresights": [{"content", "evidence", "start_time", "end_time", "duration_days"}]}`: a reply that misses or adds a key (at the top level or in an item), holds a non-string `content` or `evidence`, or a `duration_days` that is not an integer (`7.0` and `7.5` used to be truncated to 7) raises `LLMOutputError`. `start_time`, `end_time` and `duration_days` are required keys that may be `null`; the fallback to the memcell's first message, the mutual computation of `end_time` and `duration_days`, and dropping an item with blank `content` are unchanged, and the call is still made at temperature 0.3.
- **BREAKING:** `EpisodeReflector` validates its reply against a strict, default-free `_ReflectOutput` (still importable from `everalgo.user_memory.reflect`): a reply without `title` (previously stored as `""`), with an extra key or a non-string field raises `LLMOutputError`. Both reflect prompts now ask for JSON in one sentence and show the skeleton `{"content": "...", "summary": "...", "title": "..."}` they used to lack.
- **BREAKING:** every operator sends a system message of static rules and a user message holding only the call's data, instead of one user message. The prompt constants are replaced: `EPISODE_GENERATION_PROMPT` and `EPISODE_DECLARE_LANGUAGE_ADDITION` by `EPISODE_SYSTEM_PROMPT` and `EPISODE_USER_PROMPT`; `ATOMIC_FACT_FROM_TEXT_PROMPT_EN` by `ATOMIC_FACT_FROM_TEXT_SYSTEM_PROMPT` and `ATOMIC_FACT_FROM_TEXT_USER_PROMPT`; `FORESIGHT_GENERATION_PROMPT` by `FORESIGHT_SYSTEM_PROMPT` and `FORESIGHT_USER_PROMPT`; `REFLECT_EPISODE_PROMPT` and `REFLECT_EPISODE_UPDATE_PROMPT` by `REFLECT_EPISODE_SYSTEM_PROMPT` / `REFLECT_EPISODE_UPDATE_SYSTEM_PROMPT` with `REFLECT_EPISODE_USER_PROMPT` / `REFLECT_EPISODE_UPDATE_USER_PROMPT`; and each Episode-path profile prompt (`PROFILE_{INITIAL,UPDATE,COMPACT,REGROUP}_FROM_EPISODE_TEXTS_PROMPT`) by a `*_SYSTEM_PROMPT` and a `*_USER_PROMPT`. The system constants hold no placeholder, the data slots are snake_case (`{{time}}` and `{{episode_text}}` for atomic facts, `{{user_id}}`, `{{user_name}}` and `{{conversation}}` for Foresight; the MemCell atomic-fact prompt's `{{TIME}}` is `{{time}}`), the language rule appears once instead of at head and tail, the reply skeletons parse as JSON, and Markdown headings became XML-style tags. `assemble_system_prompt` appends the call-level blocks, so a prompt cache shares every static block whatever a caller passes.
- **BREAKING:** `prompt=` is removed from every operator, and a host's text goes in `custom_instructions=` where there is one. `EpisodeExtractor.aextract`, `ProfileExtractor.aextract` and `aextract_from_episodes`, `AtomicFactExtractor.aextract_from_text` and `EpisodeReflector.areflect` take `custom_instructions=`, which appends to the bundled rules instead of overriding them (on `EpisodeExtractor` it used to replace a bundled default): the text is sent verbatim, never rendered as a template, as a `<custom_instructions>` block closing the system message (an `<additional_requirements>` block on the Episode-path profile stages, an `【Additional Requirements】` section before the data on the MemCell path), and `None` or a blank string adds nothing. `AtomicFactExtractor.aextract` and `ForesightExtractor.aextract` drop `prompt=` with nothing in its place. No way is left to replace a bundled prompt, which is the point: a replacement also dropped the reply shape and the rules on what may enter the output. For `ProfileExtractor` the instructions now reach every stage the call runs (INIT or UPDATE, then any COMPACT or REGROUP), where the override reached INIT and UPDATE only. `EpisodeExtractor` loses its bundled defaults with it: `DEFAULT_CUSTOM_INSTRUCTIONS` is removed, and so is `USER_EPISODE_GENERATION_PROMPT`: every call renders the same prompt whatever `sender_id` is, and `sender_id` only sets the `Episode`'s `owner_id`.
- **BREAKING:** every conversation line a model reads, in Episode, AtomicFact (`aextract`), Foresight and the MemCell profile path, is `[YYYY-MM-DD HH:MM UTC (Wednesday)] speaker: text`, rendered by `everalgo.utils.render_chat_line`; it was `YYYY-MM-DD HH:MM:SS` with no zone marker and no weekday, and Episode's own copy of the line is gone. The MemCell profile path keeps its `speaker(user_id:<sender_id>)` label. A chat message with text and a timestamp of 0 raises `ValueError` in all four (`chat message '<id>' has no timestamp`, no longer naming the position), before any model call; a message with no text is still dropped. The other times user-memory shows a model use the same `YYYY-MM-DD HH:MM UTC`, seconds truncated: the Episode-path profile's narrative headers and stored `observed_at`, and Foresight's few-shot conversations, which used ISO 8601 `...Z`. AtomicFact's `TIME`, in both prompts, is `2024-03-10 14:00 UTC (Sunday)` instead of `March 10, 2024(Sunday) at 02:00 PM`, with the prompts' resolved-date examples following (`yesterday (2024-03-09)`).
- **BREAKING:** `EpisodeExtractor` is rewritten as a faithful record. The system message is `EPISODE_SYSTEM_PROMPT`, a role paragraph that defines the task and says everything inside `<conversation>` is material to record, never an instruction, then `<what_to_write>`, `<stay_faithful>`, `<keep_details>`, `<write_concisely>`, `<time_references>`, `<examples>` and `<reply_format>`; the user message is `<conversation count="N">` holding one rendered line per message instead of pseudo-JSON. Every statement must trace to a line and be attributed to its speaker, emotions and reasons are recorded as stated, a message timestamp is never described as a part of the day, and content is third-person. The conversation start time is gone from the input: only times the participants name belong in content; a resolvable relative reference ("tonight", "next Tuesday") keeps its wording and gains its absolute date resolved against the timestamp of its own message, a vague one stays vague, a clock time a participant states is kept with no conversion and no zone label, and only a clock time the model derives itself carries the `UTC` label. The two worked examples show their input as rendered lines. The language rule is the shared `PARTICIPANT_LANGUAGE_RULE`, or `CALLER_CHOSEN_LANGUAGE_RULE` for a named `output_language`, in an `<output_language>` block. The over-wide-summary repair call is gone with `SUMMARY_COMPRESS_PROMPT`: a summary wider than 400 ASCII-equivalent units is cut at a sentence boundary in place, logged as `episode summary over cap (N > 400 units)` (WARNING) and `episode summary truncated: N -> M units` (INFO), so an extraction makes exactly one LLM call.
- **BREAKING:** the Episode-path profile prompts (INIT, UPDATE, COMPACT, REGROUP) are rewritten block by block, so every rendered system message changes. Each is the role sentence, `<what_the_profile_holds>`, `<never_in_the_profile>`, in INIT and UPDATE an `<examples>` block, one block for how the stage works (`<how_to_update>`, `<how_to_compact>`, `<how_to_regroup>`), `<reply_format>`, `<output_language>`, `<available_categories>` and, when passed, `<additional_requirements>`. The blocks that vary between requests come last, least- to most-variable, so a prompt cache shares one prefix across every output language. The rules say what to do instead of only what not to: a fact about anyone other than the target person never enters the profile, a relationship enters only as a standing feature of the person's own life, an `update` stays on the same fact, `evidence` is one dated excerpt or faithful paraphrase per occasion that established or changed the fact, and an implicit trait needs a pattern grounded in signals recorded in a narrative shown. The user messages carry their input as XML elements: `<narrative time="YYYY-MM-DD HH:MM UTC">…</narrative>` one per line instead of a `---` separator and a `[time]` header, UPDATE's stored profile as `<explicit_info>` and `<implicit_traits>` holding `<item index="N">{json}</item>` lines instead of `=== bucket ===` headers, and REGROUP's `<group>` element with a leading `bucket` attribute, whose reply skeleton shows the item shape of that bucket (`REGROUP_REPLY_SKELETONS`). The UPDATE pass over Episodes older than the stored profile has no system message of its own: `HISTORICAL_PASS_RULE` and the `{{pass_rule}}` slot are removed, and the one point it added is part of `<how_to_update>` for every batch (an earlier value of a dimension that already holds one goes into that item's evidence, never a new item). A batch that straddles the stored timestamp still runs as a historical pass followed by a current pass, each judged against one observation date, and both now send the same system message.
- **BREAKING:** the caller-chosen output-language rule is restated plainly for every operator, with no bold `CRITICAL LANGUAGE RULE` header, capitals or "This is mandatory": "Write every output field in {language}, whatever language the input is in, including anything already stored.", closing with "Names, user IDs, proper nouns and technical terms keep their original form." The fallbacks that apply when no language is named are restated in the same style and corrected to name what their prompts contain: the Episode INIT fallback names the Episode narratives in `<episode_narratives>` and no longer extends `SOURCE_TEXT_LANGUAGE_RULE`, which keeps its wording for the operators that have an `EPISODE_TEXT`; UPDATE, COMPACT and REGROUP take the language most of their input is written in; `REGROUPED_PROFILE_LANGUAGE_RULE` is new (REGROUP sees one group's items, not the profile); and the MemCell stages get `MEMCELL_EXISTING_PROFILE_LANGUAGE_RULE`, `MEMCELL_COMPACTED_PROFILE_LANGUAGE_RULE` and `MEMCELL_REGROUPED_PROFILE_LANGUAGE_RULE`, which name the 【Stored Profile】 and 【Items】 sections their prompts use. A profile is written in one language: the Episode UPDATE updates every stored item written in another language than the one `<output_language>` gives, even when no narrative mentions it, so a stored profile that is already mixed converges on one language. A translating update changes the description, so it moves the item's `observed_at` to the batch's time, and in a batch older than the item it is refused as a stale rewrite until a current batch comes; the first UPDATE after a host starts naming a language may rewrite every stored item, which the reply budget has to allow for. The wording and the convergence behaviour have not been re-measured.
- **BREAKING:** `BoundaryDetector` is `everalgo.boundary.BoundaryDetector`, re-exported unchanged, and `everalgo.user_memory.boundary` holds nothing but the re-export. `adetect` now also accepts tool items and gains `hard_token_limit` / `hard_msg_limit`; the default hard limits of `adetect` and `adetect_step` are 65536 tokens and 500 messages instead of 8192 and 50, so inputs between the two reach the model instead of being force-split first. `DetectionResult.should_wait` is renamed `tail_complete` and its polarity is reversed: `True` means the trailing segment already forms a complete episode and can be closed now, `False` that it is held for the next batch, and `adetect_step` still returns `None`. See `everalgo-boundary` for the details.
- `ProfileExtractor` reads and writes profile items as the typed `ExplicitInfoItem` / `ImplicitTraitItem` from `everalgo-core` instead of dicts; prompts, merge results and log lines are unchanged and host keys on an item still ride through every merge. The `reason=target item is not an object` rejection is gone, since `Profile` now refuses such an item before any stage runs.
- Stored items are shown to the model with their own fields only (`evidence`, `basis`, `description`, `category`, `trait` and `observed_at`) in every stage that renders them: keys a host attaches to an item, such as `item_id` or `source`, are left out of the prompt, and are still stored and kept through every merge. A narrative or a stored item whose text spells out one of the prompts' own closing tags (`</narrative>`, `</episode_narratives>`, `</item>`, `</explicit_info>`, `</implicit_traits>`, `</stored_profile>` or `</group>`, in any case) is rendered with that tag's `<` replaced by the fullwidth `＜` (U+FF1C), so it cannot close an element early; nothing else is escaped.
- Both UPDATE prompts say an `update` operation restates the whole item (its category or trait, its description and its evidence or basis, unchanged ones included) instead of relying on omitted fields keeping their stored values; the MemCell UPDATE example gains the `category` it lacked and the MemCell REGROUP skeleton is a complete item instead of `{...}`, so every example the prompts show passes its stage's model.
- Duplicates dropped by the profile's dedup are reported as one WARNING per deduplicated list, `profile duplicates dropped: source=... count=N`, instead of one `profile duplicate item dropped` line per item. The four REGROUP log lines name the group by `bucket=` and `label_len=` instead of `label=`, which the model writes. Both `ProfileExtractor` entry lines log `output_language` after validating it, as the `OutputLanguage` value (`None` when unset), so an unsupported value is refused before it can reach a log record.
- `everalgo.user_memory.profile` and `everalgo.user_memory.episode` are packages instead of single modules. `from everalgo.user_memory import ProfileExtractor` and `from everalgo.user_memory.profile import ProfileExtractor` (likewise for `EpisodeExtractor`) are unchanged, and so are the merge results; every log line is still logged on `everalgo.user_memory.profile` or `everalgo.user_memory.episode`, with the log-line contract in the package docstring. Private names (`_apply_ops`, `_build_summary`, the `_PROFILE_MAX_*` caps, the reply models, `_truncate_at_sentence_boundary`, ...) are no longer attributes of the package; they live in the submodule that owns them.
- Foresight's date handling goes through `everalgo.utils.parse_utc_date` / `format_utc_date`, accepting and producing the same `YYYY-MM-DD` dates as before; an `end_time` that would fall past year 9999 is now dropped (`None`) instead of raising `OverflowError`.

### Fixed

- A profile over the total cap after UPDATE is compacted and then checked group by group, like a profile under it: every category or trait name COMPACT leaves over its cap of 8 items, or holding an item past the width backstop, is regrouped in the same call. COMPACT's result used to be returned as it came back, so such a group stayed over its cap until the next UPDATE. A call past the total cap now costs COMPACT plus one REGROUP per such group. Both paths.

## [0.8.0rc9] - 2026-09-14

### Changed

- The UPDATE historical pass now carries a rule of its own: a dimension that already holds a value is left alone and its earlier value is never added as a new item, so a backfilled narrative can no longer reintroduce a superseded value as a sibling of the current one. Only dimensions with no value yet are added, and existing items may still gain evidence. The current pass renders an empty rule slot, so its instructions are unchanged.

## [0.8.0rc8] - 2026-09-08

### Changed

- **Breaking:** `ProfileExtractor.aextract_from_episode_texts(episode_texts: Sequence[str], *, timestamp, ...)` is replaced by `aextract_from_episodes(episodes: Sequence[Episode], ...)` (sync bridge `extract_from_episodes`). Each Episode's own `timestamp` is its observation date; the batch may arrive in any order and is sorted internally, each narrative is rendered under its date, and the explicit `timestamp` argument is gone. Passing a non-`Episode` item raises `TypeError`.
- Profile merging is now time-aware. Every `explicit_info` / `implicit_traits` item carries `observed_at` (epoch ms), the observation date of the source that last established its description; `Profile.timestamp` becomes `max(stored, batch)` and never moves backwards. An UPDATE whose source is older than a stored item can add facts and grounding but can no longer rewrite that item's description or delete it — such operations are dropped with `reason=stale evidence`. This applies to the MemCell path too. Items written before the field existed are read as the stored profile's timestamp; items rewritten by COMPACT / REGROUP take the profile's timestamp; any `observed_at` the model writes is discarded.
- `aextract_from_episodes` in UPDATE mode splits a batch that straddles the stored `Profile.timestamp` into a historical pass (older Episodes, additions only) followed by a current pass, so one mixed backfill batch costs at most one extra LLM call and cannot let a newer narrative's date vouch for an older narrative's rewrite.
- Episode Profile prompts explain the per-narrative observation date and, in UPDATE, the rule that older narratives never rewrite newer state; the implicit-trait gate now lets a stored `explicit_info` item stand as one of the two required cross-Episode signals, so single-Episode incremental batches can still ground a trait.

## [0.8.0rc3] - 2026-09-01

### Added

- Episode extraction now uses declare-then-write when `output_language` is unset: the model declares `user_language` before generating the episode, and the normalized language is exposed on `Episode` for downstream extractors to pin their output language. Explicitly pinned calls expose the pin value without adding the declaration task.

### Changed

- Episode titles now emphasise the core event and key outcome instead of a date-heavy session label, use fewer than 20 words without a minimum or artificial padding, and include the owner's name only when needed to disambiguate participants.
- Generic and user-centred episode prompts now share one relative-time contract: the conversation start is context only; resolvable references use the containing message's timestamp and preserve their granularity; vague references such as `recently` stay vague instead of gaining invented bounds. The worked `last week` example now names its reference timestamp and ISO Monday-Sunday week convention.
- Episode generation prompts now require summaries to remain faithful to the content without inventing facts or distorting their meaning.
- Episode summaries now use a 400-unit hard width cap aligned with the 50-English-word generation target, and an over-cap summary is repaired from that summary alone rather than regenerated from the full episode content.

## [0.8.0rc2] - 2026-08-30

### Added

- `EpisodeExtractor` logs its key branch points, so one extraction reads as one story in the
  log: an INFO entry line (item count, rendered size, template, output language), the summary
  width guard's tier boundaries — entering the compress repair at WARNING with the original
  width, a successful repair at INFO with the width change, joining the existing repair-failure
  and truncation warnings — and an INFO exit line with the product widths. The tier-2 rate IS
  the production model's violation rate and repaired-vs-truncated its repair success rate;
  neither was previously observable anywhere.
- `ProfileExtractor` gets the same treatment: an INFO entry line (mode INIT/UPDATE, memcell
  count, existing item counts, output language), UPDATE's applied-ops stats, the maintenance
  routing decisions with their criterion values — total-cap breach entering full compact at
  WARNING, a group-level breach entering the scoped regroup at WARNING with the group's size —
  the compact and regroup results, and an INFO exit line with the final item counts. Joins the
  pre-existing warnings (malformed regroup items dropped, label still over cap, rejected ops,
  duplicates).

## [0.8.0rc1] - 2026-08-29

### Added

- **`EpisodeExtractor` enforces a summary width cap (400 ASCII-equivalent units, ~65 English words / ~200 CJK characters) with a three-tier guard that never raises**: a compliant summary passes untouched; an over-cap one triggers one repair call over the extracted `content` alone (`SUMMARY_COMPRESS_PROMPT`, plain-text output); a repair that fails or still exceeds the cap degrades to sentence-boundary truncation, the ellipsis replacing the final terminator — whole model-written sentences only, hard-cut solely when no sentence terminator fits the budget. Raising was rejected by the caller's failure model: the cloud add path retries the WHOLE extraction on error and drops the episode after the last attempt, so an exception over the display preview would cost the main product. Production motivation (2026-08, s0002 pool): with a qwen3-4b finetune on the episode scene, 22.1% of a month's summaries exceeded 400 units (30,169 rows, max 9,038 chars) — the model restated `content` as `summary` (top offenders' summary length ≈ body length), and nothing in the engine or the store bounded the field.

- **Full-profile compaction fires on the TOTAL cap only; a per-label breach (count or width) routes to a new group-scoped REGROUP pass** (`PROFILE_REGROUP_PROMPT`) whose legal moves are split / rename / merge-restatements — deletion is named as not a cap tool, and bucket moves are forbidden. Measured: whole-profile compact triggered by one overcrowded label dropped 6 of 13 gold facts in a single noise round (items in never-breached groups were rewritten away) and oscillated 12→8→13→8 as re-fed history restored them; the scoped pass leaves bystander groups byte-identical.

### Changed

- **The episode `summary` field spec is rewritten around compression**: "1-3 short sentences (at most ~50 English words / ~100 Chinese characters)" with an explicit COMPRESS-never-restate instruction, replacing "Under 50 words" — a word count has no clear definition for CJK output, and restating `content` wholesale was the dominant observed failure, which the old spec never addressed. The faithfulness clauses (no new facts, no self-reference, time format follows `content`) are unchanged. `ascii_width` moves to a shared `_width` module (profile's backstop and episode's cap use one yardstick).

- **`ProfileExtractor`'s item contract inverts: one FACT, one item — a category is a group key that many atomic items share, not a unique key whose single item absorbs every fact of its dimension.** v1's one-item-per-dimension packing put all growth on the item LENGTH axis, which nothing governed: a production profile reached a single 722-character `description` whose evidence chained seven dated quotes, and the fold path (an `add` whose label was taken got its prose `"; "`-joined into the owning item) guaranteed every such profile kept growing. Growth now lands on the item COUNT axis, where dedupe, caps and maintenance already govern. Measured over a 720-run lifecycle matrix (2 impls x 3 models x 2 corpora x 15 reps, 9-round INIT→UPDATE lifecycles on gold-annotated corpora): max description 123-294 chars against baseline 564-1483, mean full-fact recall within 0.47 of baseline everywhere (rule was ≤1.0), noise-round churn ≈0.
- **Two gates admit an item: it must be a fact about THIS PERSON, and only then does said-it decide the bucket.** A rule that would hold for whoever sat in the seat — a team process, an SOP — is nobody's portrait fact, however clearly the person stated it; its personal side (they set this rule for you) may enter. Deleting the old inclusion example alone changed nothing (5-7 SOP items per project-corpus run, unchanged); the gate halved the worst cell (6.27 → 3.13 hits per run). Residual leakage is expected to be cleaned per-item by the downstream stock-migration audit, not by further prompt pressure.
- **`implicit_traits` is redefined as latent traits inferred from the conversation — a grounded inference whose `basis` names the signals — and drops its `evidence` field** (`{trait, description, basis}`; basis is the grounding). The old wording defined the bucket as explicit_info's complement ("the half they did not state outright"), which reads as a filing instruction rather than an inference task: under it qwen3-235b produced zero traits in 15/15 runs on a corpus carrying two planted cross-topic dispositions. The inference framing alone took it to 2.33 traits per run with 27/30 planted-disposition recall, same model, same corpus.
- **UPDATE's `add`/`update` split is decided by the fact, not the dimension**: `add` is for a fact not yet on file (a sibling under an existing category is the intended shape); `update` acts on the same fact only — correction, contradiction, sharper wording, fresh evidence — and never widens an item to absorb a neighbour.
- **Caps: 60 items total (was 30), 8 per label, and a 250-unit width backstop per description, measured in ASCII-equivalent width units** (East Asian Wide/Fullwidth = 2, everything else 1) so one threshold holds across languages with no per-language table — 200 units reads as one-to-two short sentences in English and CJK alike. 60 covers v1's 30 dimensions at two atomic facts each; compliant-item p95 measured 183-198 units on the English corpus, so the 250 backstop catches the runaway tail without policing compliant items.
- An `add` whose label is already in use keeps the stored spelling (label canonicalisation) and lands as a sibling — the fold path is removed entirely; prose is never machine-joined.
- Prompt layout is uniform and instructions-first: task line → portrait definition → item rules → call-specific semantics → output shape → language anchor → data LAST, with every data reference naming its actual section (the old INIT opened with "read the conversation below" followed by the rules).

- The trait threshold relaxes from "two or more signals" to "one clear signal or more", with the qualitative requirements — a signal is something the person **chose or asserted**, never an operation they carried out — left untouched. Measured on a corpus built to force `implicit_traits` (two dispositions, two signals each, deliberately cross-topic and never stated outright), the two-signal bar was satisfied by no model: the four models that produced traits at all named a single signal in their `basis` 0/20 across the grid, and six of nine contemporary models produced nothing at all. The count requirement was layered on top of the qualitative wall that actually keeps one-off actions out; the wall stays, the count aligns with what every model does.

### Fixed

- The compact path's `{target_user}` injection is now guarded by a test, closing the one rendering hole the other two paths already had pinned. The naming example in the spliced `_ITEM_RULES` block must name the actual speaker — a fixed stand-in measured `implicit_traits` at 0.00/0.05/0.00 per run over three repeats against a same-version spread of 0.05 — and `_compact` receives `display_name` and `sender_id` as keyword-only arguments, which guarantee they are passed but not that they are passed correctly: swapping `target_user=display_name` for `target_user=sender_id` left all 122 profile tests green. The new test captures the compact render and asserts the interpolated example names the speaker and rejects the raw-id form.

## [0.7.0] - 2026-08-20

### Changed

- **`ProfileExtractor`'s three prompts are rewritten around one definition of what a profile is.** Measured against 20 runs of an eight-round transcript containing nothing but operations — commands, tool output, the assistant's replies, no self-description — the previous prompts produced **8.0 `explicit_info` items per run, one per conversation, 86% of them a single action restated as a standing capability** (`负责测试执行`, `具备调试能力`), with one category repeated 7 times at the median. That corpus carries exactly one thing a portrait should hold — one voiced preference — and it now yields **2.5 items per run with that preference kept in 19/20 runs**, capability phrasing among them down to **0.2-0.55 per run**. Every number in this entry is measured on the prompts as they ship here; an earlier draft of this entry quoted **0.00** for this corpus, taken before a round of prompt compression that was never re-measured and cost roughly 4x on it. See "Known limitations" for what still gets through.

  Ten rules do the work. Each one's numbers are the before/after of the round that introduced it, not of the finished prompt — rules interact, and several of these were measured again later at different values:

  1. **A profile is a portrait of a person, not a log** — stated positively, with the corollary a model will not infer on its own: a long, eventful conversation can correctly yield nothing. Neither prompt had ever said what a profile *is*; INIT opened with "build a user profile" and, given a transcript of operations, the model guessed "log". This single rule took capability phrasing from 0.80 to 0.20 items per run after four rounds of prohibitions had plateaued.
  2. **`explicit_info` holds what the person *stated*.** A property you would have to infer from an action belongs in `implicit_traits`, not here reworded. The bucket previously carried no constraint beyond "objective facts and current status", while `implicit_traits` had carried "not one-off events or short-term states" all along; the asymmetry was the gap. An earlier attempt framing this as durable-versus-one-off measured *worse* — describing the bucket as holding "skills the user demonstrably holds" reads as an invitation to summarise actions into skills.
  3. **A stated fact still has to be durable.** The pre-fix prompt asked for "objective facts and **current status**" outright; removing that phrase stopped requesting a passing state but never forbade one, and the model kept filing them. `我今天有点累` produced an item in **20/20** runs under a category the model itself named `当前状态` — it recognised the thing as transient and recorded it anyway. `Profile` has no per-item expiry and the delete rule needs a later conversation to revisit the item, which a conversation that never mentions tiredness again will not do. Now **0/20**.
  4. **Either bucket may be empty, and often should be.**
  5. **One item, one dimension.** Facts about one dimension extend one item; unrelated dimensions never share one. Two failures sit either side: rule 4 alone made the model *pack* rather than drop (one run compressed eight conversations into a single 201-character description chaining six activities, which an item-count metric reads as an improvement), but forbidding all merging was equally wrong — three items reading `主要使用Python` / `也会写Rust` / `拒绝JavaScript` are one dimension and belong in one item.
  6. **One item per category, and the category name must be reused.** The per-dimension rule only binds when names match, and a freely coined name does not: one dimension drew **eight near-synonymous names** across 20 runs (`工作环境` / `代码管理规范` / `工作规范` / `工作流程工具` / …), each admitting a second item. Reserving `add` for a dimension not yet on file, requiring reuse of an existing name, and giving "one dimension" an applicable test (dimensions are coarse; two facts share one when a reader would look for them in the same place; when unsure, it is not new) moved a same-dimension fact from `update` **3/20 → 10/20 → 15/20** and category collisions from **18/20 → 0/20**.
  7. **Uniqueness cuts near-synonyms; it never merges distinct dispositions** — without this, rule 5 reads as "compress" and the packing moves into a trait's description, where the length metric was not looking (trait descriptions went 35 → 69 characters mean, 79 → 280 max).
  8. **Nothing stands in for the subject, in `description` or in `evidence`.** All 102 measured items had opened with such a word. Banning only the `user_id` left the display name in its place. `evidence` then stayed at **71/71** (`用户明确表示…`) after `description` reached 0/71 — what moved it was not the rule but an example: the evidence rule read `e.g., "In Oct 2024 user mentioned..."`, demonstrating the phrasing the rule forbade. **The model follows the example over the rule.** Rewritten, evidence went to **0/71** and its quotes became verbatim rather than paraphrase-plus-inference.
  9. **The trait bucket needed a purpose, and "signal" needed a threshold.** Rules 2, 5 and 7 are each correct and together they nearly emptied `implicit_traits`: on a corpus with three substantive self-statements, traits fell from 4.55 per run to **0.25, with 15/20 runs holding none**. A positive definition (this bucket is the half of the portrait the person did not state outright; a conversation with substance should not leave it empty) plus a threshold restore it. The threshold matters: loosened alone, operations supplied the evidence — 17/34 traits cited a branch switch or a test run. **A signal must be something the person chose or asserted, never an operation carried out; two actions are not two signals about who someone is.**
  10. **Capability items already on file are deleted, not merged.** An item asserting a duty, capability, skill or familiarity is not rescued by the evidence attached to it: that evidence records an occasion, the claim asserts a standing property. Compaction merged 22 such items into 2 until told delete-before-merge and that twelve of them become **zero** items, not one; it now takes 29 down to 1.9 while keeping every legitimate item (**30/30** across three profile sizes).

  **The three prompts now splice in two shared constants** (`_PORTRAIT`, `_ITEM_RULES`) rather than each carrying its own wording. That is what stopped compaction drifting behind: it had gone on merging items and refining tags under the pre-fix rules, undoing the other two paths on the one call that rewrites everything. Measured before the rewrite, compaction left 20/91 items naming the subject, 10/51 passing states, and brackets on **40/40** traits where the other paths had 0/44 — the only difference being an `(e.g., [Risk-Averse])` in its own text.

  Verified in both directions against measured pre-fix baselines. On a corpus where the person does state things about themselves, all three statements survive **20/20** runs before and after — the tightening costs nothing on recall — while the operational noise beside them drops out and capability phrasing goes to **1/60** (the other apparent hits are the person's own refusals, which a keyword check reads as capability claims). `implicit_traits` stays populated there at **0.95 items per run**, and empty on the operational corpus, which is the distinction the bucket is for. Single-utterance boundaries hold: `我是软件工程师` and `我不用 Windows，只在 macOS 上开发` stay at 20/20, `我今天有点累` and `切一下分支` at 0/20. At the operation level (recording what the model emits, not just the resulting profile) a correction lands as `update` 20/20 and reaches the stored description 20/20; a dimension not yet on file lands as `add` 20/20.

  A five-turn walkthrough — a role statement, a process constraint, a refusal, a purely operational turn, then a contradiction — passes every check in **19/20** runs, against **4/20** for the version before this round. The four checks are one item per dimension (**20/20**), the operational turn changing nothing (**20/20**), a stated fact filed in `explicit_info` rather than restated as a disposition (**19/20**), and `basis` naming the signals it read rather than restating the two-signal requirement (**20/20**). The last two were **5/20** and **20/20** before; the `basis` regression came from the same unmeasured compression, which had replaced the field's JSON placeholder with `"..."` and left it undefined.

  Compaction, given a 48-item profile in which every item carries a defect, returns **9.9 items**: no item names the subject (**0/199**), no passing state survives (**0/119**), no trait carries the bracketed tag format (**0/80**), and the new fact from the accompanying conversation lands in **20/20** runs. **27/119** surviving explicit items still read as a capability, so compaction reduces rather than eliminates them.

  **Known limitations.** A **record of the work** still reaches `explicit_info` on a purely operational corpus at roughly **1.4-1.8 items per run** — what the assistant explained about the code, what a tool turned out to support, a threshold that was changed. These are durable and assert nothing about the person, so neither the durability rule nor the capability ban reaches them. Four separate rules were written against them and **each one regressed something else** (one tripled the item count on that corpus; another dropped the operational-turn check from 20/20 to 8/20); all four are documented in the module docstring so the attempt is not repeated blindly. Two properties of the measurement bound every number here: the corpora are hand-written software-engineering conversations in Chinese against one model, and the per-run item counts on the operational corpus carry a same-text spread of **±0.4**, so differences below about 1 item per run on that corpus are not evidence.

  Two properties of these prompts are easy to break while tidying them, both documented by guards:

  * **A rule repeated in two places may be load-bearing.** Removing one copy of the "also / as well as / comma-list" prohibition as a duplicate raised explicit items from 0.63-0.75 per run to 1.30-1.40 — two non-overlapping ranges against a same-version repeat spread of 0.05-0.12 — and the regression appeared in `explicit_info`, which the trait rule does not govern. The prompt's signals are not partitioned by section.
  * **An example beats the rule it contradicts.** Beyond the two cases above, rewriting the output examples in two different shapes (one flat single-line, one indented three levels) had the model write a single line and close it with the nested example's brace count: **6/20 runs produced unparseable JSON**. Both examples now share one shape.

- **Compaction now runs as soon as the item limit is reached, not 50% beyond it** (`_PROFILE_COMPACT_THRESHOLD` is `_PROFILE_MAX_ITEMS`, was `× 1.5`). Compaction is the path that removes items which were never portrait facts, and UPDATE cannot do that job: it sees a snapshot plus one conversation and acts on what the conversation raises. Told to audit the whole profile unconditionally, it emitted the deletes in **1 run out of 10** and otherwise answered `none` with `update_note: 现有档案无须清理` — it had read the instruction and judged the items acceptable. The instruction was therefore removed rather than reworded, and cleaning moved to the path that can do it. A 32-item profile carrying 29 capability items now comes back with 1.9 of them; at the old threshold it would have had to reach 46 items first.

- **The UPDATE prompt is shown the category / trait names already in use**, listed ahead of the indexed JSON. Deciding add-versus-update is a comparison against those names, and asking for it inside a wall of JSON is what let near-synonyms through. Item numbering is untouched, so every op index resolves exactly as before.

- **`{target_user}` is the speaker's `sender_name` when the conversation carries one**, falling back to `sender_id`. Previously the raw id was injected as the label and the model wrote it into the output: every `description` in a measured run began with the raw speaker id. The id remains the locator — it is what the prompt matches speakers by, and it is now passed separately as `{target_user_id}` — because `sender_name` is optional and not guaranteed unique, while single-subject attribution is the strongest requirement these prompts carry. Neither is written into output.

- An `update` that rewrites a `description` must carry its matching `evidence` in the same operation, since fields omitted from an `update` keep their stored values. Observed otherwise: a `description` updated to "cancelled the trip" while its `evidence` still quoted "I booked the trip".

## [0.5.0] - 2026-08-19

### Added

- **`output_language` on every LLM-backed operator in this package** — `EpisodeExtractor`, `AtomicFactExtractor`, `ForesightExtractor`, `ProfileExtractor` and `EpisodeReflector` — with an `OutputLanguage` enum exported from `everalgo.user_memory`. Name a language and the model is told to write in it; omit it and the model infers the language from the conversation, as before. Eight prompt variants were measured over the same prompt body — 1750 calls each, five models, thirty-five conversations covering weak language signal, pasted material outweighing the participants' own words, speaker IDs contradicting the conversation, word-level mixing and five non-English languages. Naming the language drifted **0 times in 1400 samples**; the best of six variants that left the model to judge drifted **10.2%**, and rewording did not close the gap: five wordings and one structural variant all landed between 10% and 26%, each fixing some conversations while breaking others, and four of the six drifted even on undisturbed single-language conversations. The cause is not the wording — Chinese characters anywhere in the input pull the output towards Chinese, whether inside a user ID, a pasted paragraph or one term in an otherwise English sentence, while English inside a Chinese conversation does not pull back; six mirrored scenario pairs showed no exception across all eight variants. `OutputLanguage` is closed rather than free-form because the value is interpolated into prompt text, where an arbitrary string would be a directive the caller can smuggle in; an unrecognised name raises `ValueError` instead of reaching the model. Plain strings in any casing are accepted, since callers usually read this out of config.
- `output_language` on `AtomicFactExtractor.aextract_from_text` as well, with its own fallback. Left unset it keeps inheriting the language of the `text` it was handed — an easier judgement than the one `aextract` faces, since `text` is normally an already-extracted single-language narrative with no pasted material or second speaker to adjudicate, which is why it gets a one-sentence rule rather than the conversation rule's three paragraphs. Naming a language overrides that inheritance, so a caller can turn an English episode into Chinese facts.
- `output_language` on `EpisodeReflector.areflect`, closing the last operator that had no way to be told a language. Left unset each mode keeps inheriting from its own input — the episodes being merged, or the narrative being updated — which is the wording both prompts already carried. That inheritance is weaker here than for the single-input operators, and deliberately so rather than by oversight: reflection is the one path taking *several* already-extracted memories at once, so episodes that disagree on language leave the model to pick one with nothing in the prompt saying which, and an update inherits whatever the narrative already says, so a language that went wrong upstream stays wrong through every later merge. Callers merging episodes they cannot guarantee agree, or correcting a narrative already in the wrong language, should name one. Not measured against the corpus: its fixtures are conversations, and reflection's input is extracted episodes.
- Shape assertions on the language rules themselves, in the default (model-free) test suite: each rule must keep its worked language examples, must not describe the output language as something the model picks, and must still say the things measurement showed to matter — read only what the participants say, ignore brought-in material however much of the conversation it fills, split inside a message rather than discarding whole ones, keep proper nouns untranslated, and leave the enumeration open-ended. These cost nothing to run and would have failed 0.4.0 at commit time.
- A model-facing regression corpus for output language, kept outside the repository. Thirty-five conversations across six causes of drift, mirrored `_en`/`_zh` so a position effect can be told apart from a language preference, driven by a two-stage runner that stores raw model output and judges it separately — changing the judgement costs no API calls. It lives outside the package because it needs real models and five-figure call counts, which no commit-time suite should carry; an earlier in-tree `tests/language_drift/` attempt was retired in favour of it.

### Changed

- **BREAKING: `EpisodeExtractor` and `EpisodeReflector` now require the model to write a `summary`.** Both episode prompt variants and both reflect prompts ask for it, and `aextract` / `areflect` raise `ValueError` when it is missing or blank rather than substituting a value — there is no honest preview to invent for one the model did not write. Note `EpisodeExtractor` has no retry and does not use Structured Output, so a model that omits the field costs the whole episode; that is the accepted price of not handing the caller a silent placeholder. `EpisodeReflector` is on Structured Output, where the schema enforces the field.

  The field is spelled out as: a faithful preview of the episode, readable on its own without the body, naming the main participants and the outcome reached, introducing no fact the body does not already carry, never referring to the record itself (`this conversation`, `the above`), and under 50 words. Times, when mentioned, follow the same format the body uses — the rule constrains format, not coverage, since one dual-format timestamp can eat a seventh of the budget.

  `summary` is listed after `content` in every field spec, example and schema. The model emits JSON left to right, so a `summary` placed first would be written before the narrative it summarises, making it a second independent pass over the conversation instead of a compression of the record. A test asserts the ordering in all four prompts, because it is invisible at a glance and an edit that tidies the JSON example would silently break it.
- Previously `summary` was a blind `episode[:200]` slice. The prompts never asked for it, so the extractor's `data.get("summary")` branch was unreachable from the first commit — a port artefact: the consumer side came over from the opensource `episode_memory_extractor.py`, whose LLM contract had the field, and the prompt side did not. Upstream was consuming the truncation.
- **The language rule the four extractors send when `output_language` is not given.** It now states the positive test — read the sentences the participants address to one another — instead of asking the model to recognise pasted material by its prose style, lists what to ignore concretely (a pasted document, a code block, an error message, a quoted passage, a link's contents) instead of defining it abstractly, says that such material usually shares a message with the speaker's own words so the split happens inside a message rather than by discarding whole ones, and keeps its worked language examples open-ended (`and so on for any language`) rather than naming Chinese and English alone. Each of those four came from a measured failure of the previous wording; the enumeration in particular cannot be dropped — removing the examples took Russian conversations from 0% to 22.5% drift — nor closed to two languages, which pulled third languages towards Chinese. This is the best-measured of six self-judging variants and the only one that never drifted on undisturbed single-language conversations, but it is still a **10.2%** wrong-language rate against 0 for naming the language, and its failures skew towards writing Chinese where English was wanted. Callers who care about output language should pass `output_language`.
- Prompts splice their language rule through a `{language_rule}` placeholder, stated at head and tail, rather than embedding the text. A caller-supplied `prompt=` that keeps the placeholder inherits output-language control; one that drops it silently opts out, which is `render_prompt`'s existing behaviour for any absent placeholder.
- Profile INIT gets its own fallback rule instead of the plain conversation rule. It is the participant rule verbatim — so the eight-arm measurement still describes the judgement it asks for — plus the sentence the pre-`output_language` INIT prompt carried: this is the call that fixes the profile's language, and every personality tag must be written in it too. Without that sentence INIT was the only profile path whose rule did not bind the tags, while the two paths that inherit from it both did; since tags appear in the prompts only as English examples and are model-authored free text, an unbound tag is free to stay English in a Chinese profile. What the sentence does to tag-language consistency is not itself measured — the corpus judges a profile's prose, not its labels.
- No language rule refers to its own position in the prompt any more. Each rule is spliced in at head and tail, so the profile rules' `Tag examples below illustrate format and granularity only` — wording inherited from a prompt where the rule appeared once, after the examples — pointed the wrong way at the tail. Both now say `The tag examples in this prompt`, and a test asserts no rule contains `above` or `below`.
- `ProfileExtractor` honours `output_language` on all three of its paths, not INIT alone. Pass the same language on every call and a profile's language is the caller's for its whole life, with no inference anywhere. Left unset each path keeps its own fallback: INIT follows the participants, UPDATE and COMPACT inherit the language the profile is already written in — which is what stops a later conversation in another language from splitting a profile in half, but is also unrecoverable when the language it inherits is already wrong, since every later update inherits it in turn. Naming a language on an update is how such a profile gets corrected; compaction, which rewrites every item in one pass, is where that correction lands most cleanly.

### Removed

- **`prompts/zh/` (breaking).** All seven Chinese prompt modules are gone; `prompts/en/` is the only tree. The same measurements showed prompt language dictating output language almost completely — an English prompt carrying no language rule wrote English for 100% of Chinese conversations, and the Chinese prompt wrote Chinese for 100% of English ones — which made the translated tree an implicit language switch, selected by importing a different constant and maintained by hand in parallel with `en`. Routing by input language measured 0.33% drift against 0 for naming the language outright, and only for the two languages a translation existed for; the five others fell back to `en` and drifted 100%. `output_language` covers all of them from one prompt tree. Callers passing a `prompts.zh.*` constant as `prompt=` should pass `output_language="Chinese"` instead.

### Fixed

- The runnable examples and the quick-start docs shipped a bare-array `_FORESIGHT_JSON`, while `ForesightExtractor` requires `{"foresights": [...]}`. `examples/06_full_user_memory_pipeline.py` raised on its third stage. Unrelated to the summary change, fixed in passing because the same fixtures needed updating.

### Known issues

- Leaving `output_language` unset does not handle a conversation whose participants paste a long document in another language, and no wording of the rule has: on episode that shape costs 20–27% across all six self-judging variants tried, and profile INIT fails it comparably. Passing `output_language` takes it to zero. The fixtures stay in the out-of-tree corpus so the gap remains measured rather than forgotten.
- Leaving `output_language` unset on a profile update makes the profile's language self-perpetuating: UPDATE and COMPACT inherit what the profile already says, so a language that went wrong once stays wrong through every later update. Passing a language on the update is the way out. Measured over four models on the corpus, INIT with no language named came back in the wrong language 18% of the time, so the unset path is a real route into that state.
- A profile's `category` and `trait` labels are model-authored free text, so `output_language` moves them along with the descriptions — `Location` when English is named, `居住地` when Chinese is. Callers grouping or filtering on those labels are grouping on something that now follows the language argument.

## [0.4.1] - 2026-08-04

### Fixed

- `ProfileExtractor`'s UPDATE path no longer edits or deletes the wrong profile item when one batch of operations contains a `delete` followed by an operation on a higher index. `_apply_ops` used to apply each operation to a list it was mutating as it went, so a `target.pop(idx)` shifted every larger index by one: ops meaning "drop B, edit D" over `A B C D E` edited E and left D, and "drop B and D" deleted E and left D. The indices come from `_render_profile_for_update`, which numbers the profile with `enumerate` before any operation runs, so that snapshot is the only numbering the model can see and every index must resolve against it. Collection is now separated from application — indices are validated and grouped first, updates are applied by original index, deletes are then removed in one filtering pass rather than by repeated `pop`, and additions are appended last. The old behaviour produced a structurally valid, self-consistent profile with wrong contents and emitted nothing, so a caller could neither detect nor recover from it; that made it the one defect in this batch a caller could not work around downstream. Reported by EverOS.
- An `add` in the same batch no longer widens the bound that a later `update` or `delete` index is checked against. Both bounds checks read `len(target)` at the moment they ran, so `add` + `update index=5` over a five-item list let an index that was out of range for everything the model was shown pass validation and overwrite the item just added. Indices are now checked against the bucket size as it was on entry to `_apply_ops`.
- A `type` value other than `explicit_info` or `implicit_traits` is now rejected instead of silently landing in `implicit_traits`. The bucket was chosen by `explicit_info if op_type == "explicit_info" else implicit_traits`, whose `else` absorbed everything — a misspelling, a case difference, or a missing field all routed into the wrong bucket with no trace. The two bucket names are now the whitelist, taken from the buckets themselves so the check cannot drift from what exists.
- Duplicate profile items are now removed on every path that writes a bucket. Deduplication had been delegated entirely to the prompt (`Important Rules` 5), with no fallback for a model that ignores it, and the only backstop was `_compact`, which does not run until the item count passes `_PROFILE_COMPACT_THRESHOLD` — so duplicates stayed visible for as long as the profile sat below that threshold. Identity is the item's `description` with whitespace runs folded and case ignored, since a model restating an item rarely reproduces its spacing byte for byte. Every other field is excluded, for two different reasons: `evidence` and `basis` are provenance, and the same fact quoted from a second conversation is still the same fact; the label (`category`, or `trait` for `implicit_traits`) is written freely by the LLM, so the same fact reaches `diet` one round and `preferences` the next, and keying on a label that drifts would have left a way around the dedup this adds. The earliest occurrence survives, which keeps `_build_summary`'s output — `explicit_info[0]`'s `description` — stable across successive updates. An item with no usable `description` is rejected when it arrives as an `add`, because it can be neither retrieved nor deduplicated against, but one already stored is left untouched, since it cannot be compared and discarding it would lose data.
- The dedup pass covers the whole bucket rather than only newly added items, which closes two further routes to a duplicate that an add-only check left open: an `update` that rewrites one item into a copy of another, and duplicates already sitting in a profile written before any of this existed. The second matters most — `_compact` being the sole other backstop, a polluted profile below the compaction threshold had no route back at all, and an update is now that route. Discarding an exact duplicate loses no information, which is what makes removing an item the LLM did not ask to delete safe here.
- The INIT and compaction paths deduplicate their results too; neither used to. `_init_extract` wrote the LLM's `explicit_info` / `implicit_traits` through untouched, so a profile could be born holding three copies of one item and — sitting below the compaction threshold — keep them indefinitely. `_compact` is the mechanism that exists to collapse accumulated duplication, yet its own output was never checked, so a compaction that returned duplicates simply reintroduced the problem it had just been called to solve.
- Every operation `_apply_ops` drops now logs a `warning` naming the `action`, `type`, `index`, and reason. Previously each malformed operation failed an `isinstance` check and was skipped in silence, so a partially applied batch was indistinguishable from a fully applied one and callers had no way to observe the degradation. Newly rejected-with-a-reason rather than silently mishandled: an unknown `action`; a `data` that is not an object; an `add` whose payload has no `description` (unretrievable, and nothing to deduplicate against); a boolean `index`, which as an `int` subclass used to address item 1; an `update` targeting a stored item that is not an object, which previously raised out of `dict(target[idx])` — `Profile` permits such items via `extra="allow"`. An index appearing in both an `update` and a `delete` resolves in favour of the `delete`, which answers to an explicit negation or a contradiction and so outranks a correction. Two updates on one index accumulate, matching the partial-merge semantics of a single update. The rejection logs deliberately omit `data`: it holds LLM-authored profile content, which the logging rules keep out of logs.
- `PROFILE_UPDATE_PROMPT` (`en` and `zh`) now states how an index is resolved. The prompt asks for a list of operations and its own example output puts `update` and `delete` in one array — the shape that triggered the corruption above — while saying nothing about index semantics; its only related rule stated that the two buckets are numbered independently. The new rule states that every index resolves against the profile snapshot shown above, that operations in one response never shift each other's indices, and that an item added in this response takes no index.

## [0.4.0] - 2026-07-30

### Added

- `prompts/zh/atomic_fact_from_text.py` did not exist, so callers wanting a Chinese variant of the from-text extraction path (`aextract_from_text`) had none — `user_memory`'s last en/zh prompt gap is now closed. It mirrors `prompts/en/atomic_fact_from_text.py` one-for-one, including its inherit-the-input-language rule (EPISODE_TEXT is already an extracted, single-language narrative) and its deliberate absence of mixed-input judgement clauses, which belong to episode extraction instead.

### Changed

- `EpisodeReflector`'s rendered timeline no longer brackets each episode with a `format_natural_language_time` timestamp: that value was `Episode.timestamp` (the span's closing time) in the 12-hour format this release removed, and it disagreed with the times inside the episode body itself. The bracket is dropped; each episode's own narrative is the timeline's only time source.
- `EpisodeExtractor` now rejects an empty or whitespace-only `content` field from the LLM with a `ValueError` instead of silently accepting it. A truncated or empty structured-output response is an extraction failure, and the caller learns far more from raising at the call site than from an empty-body guard firing later in `assert_episode_shape` or the benchmark extract stage.

### Fixed

- Episode output language is now defined by what the conversation participants themselves write, not by the conversation's overall character mix. Both prompt variants (generic and user-centred, `en` and `zh`) state the rule at head and tail and explicitly exclude pasted documents, code blocks, logs and long verbatim excerpts from the judgement — a Chinese question quoting a long English document now yields a Chinese episode. The generic variant previously carried no language rule at all. The rule statement itself dropped its trailing "if Chinese, ...; if English, ..." enumeration: the requirement sentence already states the rule language-agnostically, and enumerating two languages as if they were the only options only invited ambiguity for any other output language.
- Timestamps injected into the episode prompts switched to a 24-hour format (`2026-05-29 12:25 UTC (Friday)`) from the previous 12-hour, month-name one (`May 29, 2026 (Friday) at 12:25 PM UTC`). The model echoes the injected anchor's shape into its output, and the 12-hour form produced drifting formats and, in the worst case, a mistranslation of `12:21 PM` into a Chinese "before noon" phrasing. The weekday label is retained because relative-time resolution depends on it. Episode bodies are stored exactly as the LLM wrote them — code prepends nothing — so the format of the times a reader sees is enforced by the prompt rule below.
- Episode prompts: all date examples unified on `YYYY-MM-DD`.
- Episode prompts now require every absolute time that states a clock time to carry the `UTC` zone label (`2024-03-14 15:00 UTC`, never `2024-03-14 15:00` or a bare `15:00`), in all four variants (generic and user-centred × `en` and `zh`). A real-LLM run over mixed-language conversations wrote the narrative's per-event times with the label 25 times and without it 15 times, which is the same "sometimes UTC, sometimes not" inconsistency this release set out to remove. Dates without a clock time need no label, and clock times quoted from a speaker keep their original wording (`at 3:30 PM`) because the speaker's timezone is unknown.
- `EpisodeReflector`'s prompts now constrain time formatting, which they previously did not mention at all: every time carries over from the episodes being merged exactly as written, absolute times stating a clock time must keep the `UTC` label, and no episode may lose its time in the merge. Without this, reflection was the one path that could reintroduce the drift the extractor prompts had just eliminated — it rewrites the narrative wholesale, and `Episode.timestamp` is not rendered into answer context, so a time dropped here is gone for good.
- `ForesightExtractor` prompts now judge output language the same way `EpisodeExtractor` does. `prompts/en/foresight.py` and `prompts/zh/foresight.py` dropped the hard-coded "if Chinese, ...; if English, ..." enumeration and now judge language only from what the conversation participants themselves write, explicitly excluding pasted documents, code blocks, logs, error messages and long verbatim excerpts even when those dominate the conversation by volume. The `zh` prompt previously carried no standalone language rule at all — its only language requirement was a half-sentence clause tucked into the closing instruction line; that clause is now removed in favour of the same head-and-tail rule statement used by `en`.
- `AtomicFactExtractor` prompts no longer contradict the language rule they state. `prompts/en/atomic_fact.py` and `prompts/zh/atomic_fact.py` (`aextract`) dropped a hard-coded "English"/"Chinese" sentence-language mandate that overrode their own language rule; the `zh` file's rule was previously stated once, weakly, at the very end, and is now stated at head and tail like the `en` file. `prompts/en/atomic_fact_from_text.py` (`aextract_from_text`'s `EVENT_LOG_PROMPT` and `ATOMIC_FACT_FROM_TEXT_PROMPT_EN`, both on production paths) previously forced English output unconditionally with no language rule at all; both now state at head and tail that output follows the language of `EPISODE_TEXT` itself, which for the benchmark path is the already-extracted episode body — fact language now inherits episode language instead of being pinned to English. `aextract`'s raw-conversation path additionally gained the same judgement clauses the episode and foresight prompts use — since it reads the raw conversation and so faces the same mixed-input problem; its own requirement sentence is unchanged. `aextract_from_text` deliberately keeps only the inherit-the-input-language sentence, because language judgement belongs to the layer that reads the raw conversation. All rule statements also dropped the same trailing "if Chinese, ...; if English, ..." enumeration as the episode prompts, for the same reason: the rule sentence is already language-agnostic.
- `ProfileExtractor`'s three prompts now have a language rule each, stated at head and tail, with the rule matching what each call actually does. `PROFILE_INITIAL_EXTRACTION_PROMPT` is the call that fixes a profile's language: it follows the input conversation and carries the same judgement clauses as the episode prompts. `PROFILE_UPDATE_PROMPT` and `PROFILE_COMPACT_PROMPT` instead preserve the existing profile's language and must not switch even when a later conversation arrives in a different language, so they carry no judgement clauses — re-judging downstream is what would split a profile's language. All three rules now bind personality tags to the output language as well; previously tags were only ever shown as English examples (`[Risk-Averse]`), which pulled Chinese profiles towards English tags. The compaction rule also no longer cites "the input conversation content" — `_compact` receives a `Profile` only and never sees a conversation. On the `zh` side all three prompts previously had no language rule at all, while `en` had six statements; they are now mirrored one-for-one.
- `EpisodeReflector`'s prompts now state a language rule at head and tail: merged output stays in the language of the episodes being merged, and an incremental update stays in the language of the existing narrative even when the new episodes arrive in a different language. Previously neither prompt said anything about language at all, so a merged episode's language was whatever the model happened to produce — and reflection writes its result back over the same episode records. Like `aextract_from_text` and the profile update/compaction calls, these prompts inherit rather than judge: they read already-extracted episodes, so they carry no mixed-input judgement clauses. `prompts/zh/reflect.py` also stopped being a re-export of the English constants — it had been a placeholder that handed callers English prompts — and is now a real translation with the same placeholders.
- The judgement clauses now hand the model an operational test for what counts as pasted material, instead of only telling it to ignore such material. The instruction to ignore "pasted documents, code blocks, logs, error messages and long verbatim excerpts" presumes the model can tell which block is pasted, and with unmarked prose it frequently cannot: English participants pasting an unmarked Chinese document produced an English episode in only 48 of 74 real-LLM attempts, against 24 of 25 when the same document sat inside a code fence — the failure was recognition, not willingness. The clauses now define pasted material as a run of two or more consecutive sentences reading as finished prose from elsewhere — explanatory or documentary in tone, addressed to no one in the conversation, advancing no request, answer or decision of its own — and state explicitly that this holds whatever language it is in and whether or not it is wrapped in quotation marks or a code fence. Measured on the failing shape of input: 40 of 40 attempts, against a 48/74 baseline. A regression sweep over all six mixed-language scenarios (Chinese participants with English tracebacks, English with Chinese prose, fenced and unfenced, embedded English terms in Chinese sentences, Japanese with English code) scored 120 of 120 at 20 attempts each. Applied to all four extractors that judge language from a raw conversation — `EpisodeExtractor` (both variants), `ForesightExtractor`, `AtomicFactExtractor.aextract`, `ProfileExtractor` INIT — in both `en` and `zh`, 14 statements in total. The inheriting prompts (`aextract_from_text`, profile update/compaction, reflection) are untouched: they carry no judgement clauses by design.

### Known limitations

- Relative-time resolution uses UTC dates while speakers phrase relative time in their own timezone. For a UTC+8 speaker, references made during local 00:00–07:59 resolve one day early. Fixing this requires the caller to supply a timezone, which the stateless algorithm layer does not receive.
- Whether an output language is retrievable depends on the caller's tokenizer. A Chinese-only tokenizer indexes no tokens at all for Japanese kana, Hangul, Cyrillic, Greek, Arabic, Thai or Hebrew, and truncates accented Latin words.

## [0.3.2] - 2026-07-21

### Fixed

- `ProfileExtractor` no longer leaks other participants' information into the target user's `Profile` in multi-speaker conversations. INIT and UPDATE prompts now receive `sender_id` as an explicit `{target_user}` with speaker-attribution rules, and `aextract` fail-loud validates that `sender_id` is a human (`role == "user"`) speaker present in the input. Removed the never-consumed `TEAM_PROFILE_UPDATE_PROMPT` dead constant.

## [0.3.1] - 2026-06-24

### Fixed

- `EpisodeExtractor`, `ForesightExtractor`, and `AtomicFactExtractor` now pass the first message's timestamp (`memcell.items[0].timestamp`) as the conversation start time to LLM prompts. Previously they passed `memcell.timestamp` (closing time of the slice), which skewed absolute date resolution for relative time expressions.
- Episode prompt: relative time references (e.g. "last Friday", "last summer") are now resolved using each message's own timestamp instead of `conversation_start_time`. Fixes off-by-one-week errors when a MemCell spans multiple days. Per-message timestamps switched from ISO 8601 to human-readable format with weekday labels.

## [0.3.0] - 2026-06-15

### Changed

- **License relicensed from MIT to Apache-2.0** as part of the pre-open-source security audit.

### Added

- `EpisodeReflector`: merge N chronologically-ordered episodes into one accurate narrative. Two modes: INIT (full merge, `old_episode=None`) and UPDATE (incremental, `old_episode=Episode`). Uses OpenAI Structured Outputs via `response_format`. Re-exported from `everalgo.user_memory`.

## [0.2.0] - 2026-05-27

> First archived changelog. Entries below accumulated since the initial `0.1.0` PyPI release (published manually, without a git tag or per-package changelog), so this `0.2.0` section also consolidates the previously-unarchived `0.1.0` surface.

### Added

- `BoundaryDetector`: facade class wrapping `everalgo.boundary.detect_boundaries`; accepts `llm=` at construction time and manages the carry-forward `tail` across calls.
- `EpisodeExtractor`: per-sender Episode fan-out — one LLM call per unique `sender_id` found in the `MemCell`; accepts `llm=` and `prompt=` at construction time.
- `ForesightExtractor`: single `MemCell` → `list[Foresight]`; async with sync bridge via `asgiref.async_to_sync`.
- `AtomicFactExtractor`: single `MemCell` → `list[AtomicFact]`; async with sync bridge.
- `ProfileExtractor`: chronological `list[MemCell]` (last element = most recent) → single `Profile`; single-shot LLM snapshot.
- English and Chinese prompts for all four extractors under `user_memory/prompts/{en,zh}/`.
- `DetectionResult` re-export from `everalgo.boundary`.

### Changed

- `WorkspaceMemCellExtractor` is no longer re-exported from `everalgo.user_memory` (`__all__`). It was an unimplemented stub that raised `NotImplementedError`; it now lives only in `everalgo.boundary.workspace`. Re-adding it once implemented is a non-breaking addition.
- `BoundaryDetector` renamed from `UserBoundaryDetector` (which was itself renamed from `ChatBoundaryDetector`) to match the no-prefix naming convention used across the package.
- `EpisodeExtractor.aextract` parameter `owner_id` renamed to `sender_id` to align with `ChatMessage.sender_id`.
- `ProfileExtractor` signature changed from separate `memcell` + `cluster_episodes` parameters to a single `memcells: Sequence[MemCell]` list, matching the other extractor contracts.
- `Episode`, `Foresight`, `AtomicFact`, `Profile` schemas dropped `parent_id` / `parent_type` fields and the `id` field; schemas now carry only the minimal required fields plus `ConfigDict(extra="allow")`.
